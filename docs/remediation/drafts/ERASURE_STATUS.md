# Financial data erasure — work in progress, not deployable

The user's latest explicit decision is to erase the retired financial data for all users regardless of ownership and remove the retired financial feature, while preserving subscriptions, reminders, accounts, unrelated application data, and original phone SMS. The briefly considered full application reset was explicitly cancelled and must not be performed. This authorization does not mean erasure has happened.

The adjacent SQL migration is a **draft only**. It is intentionally outside the migration directory and will not run as part of normal database migrations. Do not deploy, manually run, or copy it into the migrations directory until the release blockers below have been resolved and verified. No production deletion or deployment has been performed.

## Work completed locally (not released)

- Android SMS receiver, wallet capture/cipher/storage implementations and their method-channel write/read bridges were removed. The retained subscription reminder methods, voice, archive and Focus Shield bridges remain. Focus Shield now rejects SMS-app notifications before accessing their content; its opt-in, memory-only inbox for explicitly supported non-SMS messaging apps remains. Flutter money/queue screens and client write paths were removed; the weekly Focus report no longer requests or sends spending data. Subscription CRUD still uses its existing API path. Native wallet cleanup independently attempts each preference store, each key alias and notification cleanup, and matches the retired notification channel instead of cancelling shared notification IDs (the focus timer also uses 999). On Android versions without notification channels, an old financial notification may remain until dismissed; the cleanup does not risk cancelling an unrelated notification.
- A narrow startup/sign-out cleanup attempts retired Flutter preferences, the old secure-storage token and Android wallet Keystore/preferences, independently and on every launch. It does not delete all preferences, all secure storage, subscriptions, reminders or original SMS. Native and Flutter changes passed hosted analysis/tests and an Android debug build, but have not been exercised on a device; retry and cross-platform behavior still need validation.
- Production routing mounts a dedicated subscription controller, service and PostgreSQL repository and a token-revocation-only router after the existing HTTP 410 guards. Backend SMS ingestion/analysis and token issuance were removed, retaining authenticated session-scoped legacy token revocation for mixed-version rollout. The legacy Money controller, service, repository, routes and test-only harness were removed, together with wallet-write middleware and transaction, payment, budget and report validation/DTO code. Retained subscriptions still resolve legacy categories until the draft detaches them; category-archive race and amount/scale behavior are covered against the production subscription app. Registration does not create financial categories. Historical migrations, deletion/retention cleanup and some shared database types still reference financial tables and need review. Unused retired endpoints and financial/SMS schemas were removed from the OpenAPI generator and generated document, and the sample analytics and preview no longer promote financial features. The cross-feature money reader was reviewed and reads only retained subscriptions. The erasure SQL is not in the runtime migration directory.
- The v1 account archive keeps its original ordered section names and zero counts for retired categories, transactions, budgets and SMS-ingest devices, but does not query or export those tables, including during pre-erasure rollout. The legacy metadata export also returns an empty categories array without querying categories. Subscriptions, notes, reminders and other unrelated data remain exportable; preexisting downloaded archives remain external copies. SQL-harness and isolated PostgreSQL tests cover exclusion, precision, account scoping and the preserved export contract.
- Retained active subscription reads now project renewal dates from the stored first date and anchor without recording payment or mutating data. Detail/list/search and day/dashboard use the projection; list cursor keys remain the stable stored date plus ID, so the mobile list fetches all pages then sorts displayed dates. The mobile monthly estimate uses the server's rounded four-decimal monthly equivalent, adds with integer precision separately by currency and excludes inactive subscriptions. It fails closed for malformed/duplicate pages (up to 5,000 display items; reminder snapshots retain their 200-item limit). Concurrent edits across pages can still change results; this is not a database snapshot. Targeted isolated PostgreSQL tests include past weekly dates, all query surfaces, unchanged stored rows, and 31-item pagination after the draft deletion. Mobile tests passed in hosted CI; physical behavior remains unverified.
- Current backend formatting, source/test typechecks and lint pass. All historical migrations ran through the real migration CLI on isolated PostgreSQL 16.2 with pgcrypto, citext and pg_trgm (extensions built locally), using a distinct non-superuser migrator. The full suite on this freshly migrated database passed 631 tests; the two destructive/opt-in draft tests were skipped there and passed separately: rollback/FK test on the migrated database and committed/concurrency test on another freshly migrated, dedicated disposable database. After committed erasure, 23 subscription, query and reminder integration tests also passed. The committed test additionally verifies that the restricted runtime can schedule and purge an account without deleting another account’s subscription. This local setup still cannot prove production schema/roles or deployment behavior. [Hosted CI 42217735967](https://github.com/KarimOmarShawky/life-style-app/actions/runs/42217735967) passed on commit `78e0879`, including both draft tests, Flutter format/analyze/tests, Kotlin JVM tests and a signed debug validation APK; signed release and live pilot were skipped. Retirement-marker/guard changes were locally tested; check hosted CI for the exact release commit before promotion. Root contracts passed 161/161 after guard changes. Thirteen standalone JVM renewal calculation checks passed using Java 17 and Eclipse JDT; they cover local 09:00, DST, month ends, off-cycle first dates and long-past anchors, but not Android alarm delivery. Three focused Kotlin source tests passed using the project Kotlin compiler version and temporary Android/JUnit stubs; this is not a real Android build or device test. Hosted CI performed real Flutter analysis/tests and built the offline Android debug artifact; no physical Android device was exercised.

- A mandatory production startup guard now requires an atomic marker from the draft erasure and checks runtime/assumable role write permissions before the API listener or worker consumer starts. A pre-erasure database and later PUBLIC grant failed closed in tests; a committed isolated erasure passed, and isolated actual API/worker startup rejected the old database. The non-production `REQUIRE_FINANCIAL_RETIREMENT=true` flag enables rehearsal; production cannot disable the check. This is intentionally **not deployable** until the draft is reviewed and run through the controlled release process. The guard cannot detect partial imports or later grant changes while running. ## User-provided Neon catalog observation (2026-11-06)

The user supplied read-only Neon catalog observations from a branch labelled `production`; it was initially archived and was unarchived with the user's permission for inspection. The user reported privately comparing the Railway `DATABASE_URL` with the Neon connection and finding matching hostnames, then confirmed that the configured database name is `neondb`. This is useful target evidence, but it is not an independent verification of the branch endpoint, runtime role or other writers. The SQL editor reported tables `subscriptions`, `transactions`, `budgets`, `categories`, `ingest_tokens` and `audit_logs` present, and `wallet_owned_records`, `wallet_account_sessions` and `wallet_accounts` absent from `public`. The three observed incoming foreign keys to retired tables were from subscriptions, transactions and budgets to categories, matching the earlier schema. The `lifestyle_app` role was absent. These observations are point-in-time, scoped to the inspected branch/database and query role, and do not establish row visibility, actual application connection identity, other schemas, copies or future state.

A later catalog inspection reported `reminders` present, and `pgmigrations` and the retirement marker absent in `public`. The inspected existing tables had row security disabled; the SQL editor's role owned them. The reported custom triggers included no SECURITY DEFINER trigger functions; this is not a review of other privileged functions, triggers or writers. This older, owner-managed schema has not been reconciled with the versioned migration history, and the editor's owner identity is not proof of the Railway runtime identity.

An isolated rollback-only rehearsal simulated absent wallet tables and their trigger function, with a pre-existing restricted `lifestyle_app` role (unlike the observed Neon setup). In that simulation, applying both existing wallet-schema migrations before the original draft allowed it to delete synthetic retired rows and preserve synthetic subscriptions, reminders and notes; privilege revocation and the marker were also checked. All changes rolled back. This is a compatibility experiment, **not an approved production procedure**: it did not model the absent Neon role, reconcile missing migration history, verify schema equivalence or drain real writers. Creating empty wallet tables may not be the final chosen path. The current application also reads newer columns such as `subscriptions.amount_scale`, so starting it against this older schema requires separate compatibility verification.

The user also showed Neon Backup & Restore displaying a six-hour history window and no snapshots; this does not establish a tested recovery point. Restoring an older point or creating a snapshot can retain or resurrect the financial data. A retention/deletion plan and tested isolated recovery remain necessary; no restore or snapshot was performed. The adjacent `neon-readonly-catalog.sql` is a catalog-only inspection query, syntax-checked against isolated PostgreSQL; it does not execute erasure.

**Do not run the existing draft against this database as-is.** It locks the absent wallet tables and requires `lifestyle_app`; it will fail. The current production startup guard and production configuration also require the newer schema and runtime role. Identifying the actual target and writers, reviewing schema/roles and backups, testing an adapted procedure against a representative isolated clone, and coordinating retirement with deployment remain mandatory. A sleeping Railway service is not evidence that old writers are permanently stopped. No deletion has been performed.

## Blockers

- Review remaining historical/shared financial table types and deletion/retention compatibility where safe, without dropping unrelated account, subscription and reminder coverage. Registration no longer seeds money categories, so that it does not conflict with the draft write revocation; this change alone does not erase any existing rows.
- The rollback-only draft test seeds two accounts and checks erasure, preservation, privileges and rollback; it now also asserts the complete expected catalog of incoming foreign keys to retired tables. The separately opt-in committed test requires a loopback host, an exact dedicated database name, empty user/financial/audit tables, distinct roles and a destructive-test acknowledgement. Both also passed locally against freshly migrated PostgreSQL 16.2 with all required extensions and distinct roles. The draft now aborts and rolls back if PUBLIC, inherited or assumable roles still allow retired writes or if the runtime can assume an owner/superuser role; the rollback test covers PUBLIC column grants and a separate local test covered a SET ROLE-only grant. This is not protection against later role/grant changes or privileged SECURITY DEFINER paths. Review of production schema/role inheritance, wider audit/event history and external data copies remains a release blocker. Hosted CI must pass for the exact release commit. The locks and privilege checks do not replace draining old instances or identify unknown historical storage.
- Validate the retained-subscription projection and mobile pagination/summary on physical Android devices; Flutter tests passed in hosted CI. Page-by-page list reads are not a snapshot under concurrent edits; the API documents its stable stored-date cursor order. Reminder scheduling must still be verified at 09:00 device-local two days before each renewal, including timezone changes and reboot.
- Finish and verify Android device cleanup, confirm the reviewed storage keys and aliases against deployed historical versions, verify the secure-storage cleanup on each supported platform, and ensure retired code cannot recreate local data. Startup cleanup was built in hosted CI but has not been tested on a device. Offline or never-updated installations cannot be remotely cleaned by it.
- Establish a deployment plan to drain old API instances and background writers before erasure, avoid older clients recreating data, and verify the result after deployment. Review account archives, external exports, logs, backup retention and disaster recovery: restoring an older backup can resurrect deleted data and requires reapplying a verified erasure before service resumes. External copies and original phone SMS are outside the scope of the app database operation.
- Confirm hosted CI for the exact release commit, and obtain a signed release and physical-device validation. Verify automatic subscription reminders at 09:00 local time two days before every renewal and Digital Detox / Focus Shield accessibility behavior. AI streaming/error handling still requires live/device verification.

The older retirement report describes the earlier, preservation-only baseline; read it as historical rather than as the current authorization or a claim that data deletion is complete.
