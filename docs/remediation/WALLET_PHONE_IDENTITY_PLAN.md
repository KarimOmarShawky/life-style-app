# Independent phone sign-in for wallet and bank data

Status: **implementation groundwork only; NO-GO for real SMS or release**. The user chose a wallet account independent of the main app account, entered using a phone number and SMS confirmation code. This decision applies only to wallet and bank data; it does not link goals, habits, tasks or other app data. Existing app sign-in remains separate. The user did not approve a blanket pause in SMS capture/processing.

The present code **does not implement phone sign-in**. There is no phone-login screen, provider integration, wallet-account database, authentication endpoint, independent wallet session, or newly isolated capture path. Current mobile SMS capture/processing still uses the older ownerless queues and legacy routes. In particular the user's requirement that ownerless old messages remain locked and never automatically shown/sent/deleted is **not yet met**. Do not use real messages to test this work.

## Identity and privacy boundary

- A number typed into a form is not authentication. An SMS code can establish present control of a number, subject to delivery/provider and SIM-swap risks; it cannot establish permanent ownership of the number, that a bank or wallet is owned by the same person, or ownership of a historical SMS. Numbers may be recycled, shared or changed. A number or sender label must not be used to infer an old record's owner.
- The wallet principal must have a fresh opaque immutable internal identity, distinct from the general `users` identity. Wallet-scoped credentials must never authorize other app endpoints. Existing app-account transactions cannot safely be silently moved into the new wallet principal; any future migration must distinguish manually entered data and require a separate, informed design.
- Derive a keyed, domain-separated lookup digest from a canonical international phone number rather than store or log the raw number as a lookup key. This is pseudonymization, not anonymization: compromise of the server key enables guessing numbers. Define independent high-entropy secret provisioning, rotation, backup, loss/recovery, deletion and retention before persisting or using real identifiers. Never put keys in mobile builds, source, logs, URLs, analytics or chat.
- SMS OTP proves access to the receiving number at that moment, not a forever-safe account recovery mechanism. Phone recycling, SIM swap, multi-device use and recovery of existing sensitive transactions require explicit security/product design; do not automatically disclose old financial data solely because a future claimant receives a code for the same number.
- On Android, neither a verified login number nor the inbound sender proves which wallet/account a financial SMS belongs to. Dual SIM, device sharing, delayed broadcasts, provider changes and unavailable subscription numbers complicate attribution. The capture boundary must establish a validated active **wallet** session at the SMS arrival/reservation point, constrain scope and consent, and preserve but not assign uncertain messages. Never guess from message content or the currently displayed account.

## What was added, without wiring

`wallet-phone-security.ts` provides strict structural E.164-format input, keyed/domain-separated phone lookup and OTP digests, and separately prefixed random wallet-token hashing. The opaque wallet token is not accepted by existing app-JWT or legacy ingest-token parsing; it is not yet accepted anywhere. The digit check does not establish an allocated or reachable phone number. Secret length validation cannot establish entropy.

`wallet-phone-otp-store.ts` is an unwired Redis challenge building block. It generates a six-digit code and random challenge ID, stores only the ID and keyed digest, and uses Lua to atomically enforce five-minute challenge lifetime, 60-second cooldown, five issuance attempts per phone per hour, five guesses per challenge, and 20 verification attempts per phone per hour. Atomic snapshot comparison prevents an old verification from consuming a replacement; only one concurrent correct verification succeeds. All keys for one lookup share a Redis Cluster hash tag. The issued challenge and store redact common object serialization/inspection, but explicit access to a code or secret can still leak it and the destination number must be handled by a real delivery adapter. Redis errors do not return a successful verification.

These primitives do **not** constitute a login system. Redis state loss, failover, timeouts, mixed versions and cluster behavior have not been tested; retry limits can be lost on state loss and calls can stall. There are no IP/device/global limits, anti-enumeration response policy, delivery-cost controls, provider consent/privacy review, durable delivery, delivery-order fencing, or transactional binding between code consumption and durable session issuance. A delayed/failed provider call may deliver a code after replacement or lose the only usable code. Those must be resolved before exposing an endpoint, with no pretend successful delivery if an SMS provider is unavailable.

## Required integration sequence

1. Choose/configure an approved SMS verification provider and commercial/privacy controls without collecting credentials in chat; implement real delivery and verify sender, retention, regional availability and costs. Provider absence/outage must be visible and fail closed, not silently grant access.
2. Design and test a separate wallet-account/session store and dedicated authentication routes with bounded anti-abuse, one-time OTP and durable atomic session creation, expiration, revocation, logout, device recovery and account lifecycle. Keep wallet credentials scoped to wallet/bank data and inaccessible to general app APIs. Address recycled-number and SIM-swap recovery before opening stored financial data.
3. Implement one native capture/session authority shared by every receiver and Flutter engine, plus owner-authenticated, durable record storage and atomic queue transformations/acknowledgments. Ensure the capture decision uses the wallet session active at the defensible capture boundary, not an account read after a delay. Define dual-SIM and ambiguous-number handling. Couple the legacy lock with a working new capture path rather than silently pausing all capture.
4. Build wallet-scoped transaction/review/provider APIs comparing the authenticated wallet principal against immutable record ownership. Legacy app routes and `X-Wallet-Owner` do not provide this guarantee and must not be used as an unsafe fallback. Preserve unknown-owner old records, without automatically displaying, sending, reassigning or deleting them.
5. Test logout/transition/in-flight races, storage failures, real provider constraints, rate-limit durability, mixed versions, physical Android capture and Focus Shield. A safe quarantined-message interface comes only after isolation; no automatic resend or deletion.
