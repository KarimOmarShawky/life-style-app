# Financial retirement: deployment and restore rehearsal (draft, NO-GO)

This is a preparation checklist, **not permission or instructions to run the draft on production**. The draft is outside the normal migration directory and has not been applied to production. Release still requires production schema and privilege review, independently reviewed operational steps, a successful rehearsal against a representative isolated clone, and physical Android validation. Do not copy the draft into automatic migrations yet. Never place credentials, customer rows, SMS contents, exported archives or database URLs in CI logs or tickets.

## Scope and safeguards

- Erase app-stored legacy transactions, financial categories, budgets, ingest credentials, wallet records and the specifically identified financial audit events for **all** users, including records without a known owner. Detach subscription categories but preserve subscriptions, schedules, reminders, accounts and unrelated data. Do not access or delete the original phone SMS.
- Local client cleanup runs only after update and launch or sign-out; an offline/never-updated installation, historical exports, logs and backups are separate copies. Identify owners and retention/deletion plans for each; do not claim those copies are already erased.
- This branch's API and worker **refuse to start in production** unless the atomic retirement marker exists and the effective/assumable runtime roles lack retired write permissions, except the `ingest_tokens.revoked_at` UPDATE needed by the retained route. That column grant alone does not enforce one-way revocation. `REQUIRE_FINANCIAL_RETIREMENT=true` enables the same guard for non-production rehearsals. The ordinary migration command does not run the draft. Do not bypass the guard to work around a missing marker.
- The inspected Neon database has no migration ledger. The migration runner's `--dry-run` can still create an empty ledger before simulating migrations, as demonstrated on an isolated fixture. Do not run `--dry-run`, ordinary migrations, `--fake`, or manually stamp the ledger on the real database without a separately reviewed plan.
- The marker and grants are transactional with the draft; a failed transaction must leave neither the deletion nor a new marker committed. The guard is a startup check, not an ongoing monitor: it does not detect partial table imports after startup, later privilege changes, privileged `SECURITY DEFINER` functions, old binaries, or out-of-band writers. Protect role administration and review all such paths. Data-level counts alone do not prove absence from unknown tables, old formats or external stores.

## Preparation before any change

1. Inventory the actual target, regions/replicas, DB schemas, object owners, all API/worker identities (including assumable roles and inherited/PUBLIC/column grants), scheduled jobs, triggers, `SECURITY DEFINER` functions, replication, log pipelines, caches, mobile versions and backup/export locations. Compare with the reviewed migrations and expected FK catalog. Resolve any unknown financial storage or unexpected dependency; stop if incomplete.
2. Ensure a current protected backup exists and a recovery owner has tested its restoration **to an isolated environment only**. The backup contains data slated for erasure and must be access-restricted, inventoried and handled under an agreed retention/destruction policy. Do not confuse the existence of a backup with permission to serve restored financial data.
3. Rehearse using a representative isolated clone with distinct non-superuser migrator/runtime roles, the real release binaries, and no routes to production services. Verify the guard rejects a pre-erasure clone and a clone with an inherited, PUBLIC, column-level or SET ROLE write grant. Check subscriptions/reminders and unrelated data before/after using privacy-preserving evidence, including off-cycle renewal dates and account deletion. Exercise both rollback on injected failure and committed erasure, concurrent old writers, restart, and restore. Review exact migration and lock times against representative data volume; no deletion should begin if capacity, grants, ownership or lock/drain procedures are uncertain.
4. Independently approve the final exact SQL and target, a bounded maintenance window, abort conditions, monitoring and a data/backup retention plan. Review provider and operational logs separately. This document does not approve the production action.

## Planned controlled window — subject to review

- Stop admission to all old API versions, stop/drain all background jobs and in-flight writes, verify no old writers or privileged alternate paths remain, and prevent automatic restart of old deployments. Give graceful shutdown enough time and confirm at the database and orchestration layers.
- Under a separately authorized controlled migration transaction and verified migrator identity, run only the reviewed final erasure against the confirmed target. Its locks and privilege checks do not substitute for draining. An error, timeout, unexpected role, schema, foreign key or data source is a stop condition: roll back the transaction and investigate; do not try random privileged fixes or bypass checks.
- Before allowing traffic, verify the exact targeted tables and specified financial audit classes, resulting privileges and retirement marker; verify preserved subscription schedules/reminders, unrelated data and account lifecycle, without extracting customer content. Verify all writers run only the new version and cannot reissue retired credentials or write legacy rows. Recheck replicas and backup policy. A successful SQL transaction alone is insufficient to release.
- Build a signed release against an approved staging API. Validate Android notifications and 09:00 local recurring reminders across permission changes, timezones, reboot and app updates, plus Digital Detox / Focus Shield accessibility behavior and live AI streaming/error handling. A debug/offline artifact is not release or connected-device proof.

## Restore and rollback

- A backup predating retirement has no marker: the updated production API and worker fail startup. Keep the restored database isolated; rehearse and rerun the separately reviewed erasure before reconnecting any service, replica, export, analytics or client. Verify marker, effective privileges, absence of financial records and retained data before resuming. Never restore old binaries or privileged workers to bypass the startup gate.
- A partial restore into a database that already has a marker can reintroduce old data without removing the marker. Block table-level/partial imports and replication from older stores until an equivalent reviewed, offline erasure and verification has completed. Configuration changes after startup are also not caught by this startup-only guard. Monitor and restrict those administrative paths.
- Application rollback must not roll back the irreversible data-erasure policy, privilege restrictions, marker check or SMS-retirement protections. If that cannot be established, keep service offline and escalate rather than restoring an older release. Backups, user-selected external exports and original phone SMS remain outside the database migration.
