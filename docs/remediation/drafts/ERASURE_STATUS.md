### Restricted runtime: preliminary local experiment, not a cutover

Neon's [role documentation](https://neon.com/docs/manage/roles) states that roles created through the Console, CLI or API automatically receive `neon_superuser` membership, whereas roles created with SQL do not. Therefore **do not use Neon's Add Role button for the intended restricted runtime**, and do not create any role yet: its attributes, membership, credentials, secure provisioning and endpoint still require an approved plan. Do not paste a password into a SQL editor or share it in chat; SQL editor query history and operational logs may retain sensitive statements. Managed-service specifics and effective privileges must be independently verified before any cutover.

The separate `1792900000000_runtime_grants_rehearsal.cjs` is a **local experiment only**, outside automatic migrations. It requires an already-existing non-owner, non-superuser login without other role memberships, disallows public-schema/database CREATE and existing effective table, column and sequence privileges (apart from marker SELECT), and grants named-table permissions for retained operations plus token revocation and cleanup. It neither creates the role nor sets credentials, grants unrelated tables, changes PUBLIC/default privileges or modifies other schemas. Its named retained-table CRUD grants are candidates, not proven minimally necessary. It checks the current `public` catalog only, not all schemas, default ACLs or SECURITY DEFINER functions. It assumes a fully migrated schema and existing erasure marker, neither established on Neon; the marker itself does not prove that rows cannot subsequently be restored or inserted. Failure must roll back the entire transaction. Never execute it on production.

A freshly recreated disposable local database ran the committed erasure, then **only for the experiment** revoked all local test-role table and sequence grants to simulate a fresh role, granted marker SELECT and applied the draft. It refused both a PUBLIC table SELECT and a PUBLIC column UPDATE grant; after removal, the restricted runtime passed the startup guard, could write synthetic notes, subscriptions, reminders, password-reset rows and an audit event, and could complete the existing account-deletion lifecycle. Token `revoked_at` UPDATE succeeded; token hash UPDATE and transaction INSERT were denied. SQL-level password-reset writes and synthetic reminders do not prove the complete password-reset worker, notification delivery, all application features, credentials or role provisioning. The test does not grant access to other tenants or production.

**Sequencing experiment, still NO-GO:** existing migrations can grant `lifestyle_app` broad privileges, while the new grant draft rejects pre-existing grants. A newer test, `restricted-role-sequence.test.ts`, uses a completely separate disposable PostgreSQL 16 instance with no app role at the outset. It loads the repository's synthetic schema, removes selected objects observed missing in Neon, inserts synthetic financial and retained data, and creates an unrelated fixture. A non-superuser synthetic owner adds the simulated missing non-wallet objects while the role is absent; it then creates a fresh login without credentials, applies the wallet migrations, runs the erasure draft and the scoped-grants experiment in the same transaction. The wallet migrations' temporary write grants are revoked by erasure. It verifies successful application startup guard, account lifecycle and retained fixtures, denied financial insert and unrelated-table access. Injecting unexpected PUBLIC SELECT made the grants draft fail, and rollback restored the synthetic data and removed the role, schema additions and marker. The test does not use the preceding blanket revoke.

This explores one possible order only, **not an approved production sequence**. The synthetic base is not the real schema, and the local superuser bootstrap changes the owner of an empty test database solely to establish the fixture; that bootstrap must never be used for Neon. The test uses passwordless trust on an isolated local instance, does not model secure authentication or Neon-managed role semantics, and has not reconciled the missing migration ledger. In particular replaying these migrations without an approved history strategy could later cause them to run again or fail. CI runs the test in a separate disposable PostgreSQL service. A safe production maintenance identity, managed-service transactional behavior, credential handling, other schemas, role inheritance, default ACLs, privileged functions, concurrent/old writers, backups and restoration remain unverified. Do not paste either draft into Neon.

`security-inventory-readonly.sql` is a **separate, read-only** diagnostic query for the intended database, not a migration. It collects version, role names and attributes/memberships, role-setting names (never values), ACLs, object ownership across non-system schemas, SECURITY DEFINER function metadata and source hashes, trigger/FK metadata, and a limited snapshot of connection counts grouped by role/state. It never selects customer rows, function bodies, connection strings, passwords, session queries or IP addresses. Role/object names, function search paths and hashes are still sensitive metadata; review before sharing and don't commit exports. The query reports effective privileges for login roles on specific target tables, not all possible SET ROLE, function, RLS, cross-database or external-writer paths. Missing visibility, dropped sessions, poolers and inactive/external writers prevent activity output from proving that writes are stopped. In a synthetic PostgreSQL test, the query ran in a READ ONLY transaction with the runtime role absent and present, reported injected PUBLIC column/default/function privileges and a cross-schema FK, and did not return synthetic row content, role-setting values or function bodies. This is not independent proof that the Neon result is complete or safe.
