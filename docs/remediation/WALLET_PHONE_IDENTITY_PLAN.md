## Identity and privacy boundary

- A number typed into a form is not authentication. An SMS code can establish present control of a number, subject to delivery/provider and SIM-swap risks; it cannot establish permanent ownership of the number, that a bank or wallet is owned by the same person, or ownership of a historical SMS. Numbers may be recycled, shared or changed. A number or sender label must not be used to infer an old record's owner.
- The wallet principal must have a fresh opaque immutable internal identity, distinct from the general `users` identity. Wallet-scoped credentials must never authorize other app endpoints. Existing app-account transactions cannot safely be silently moved into the new wallet principal; any future migration must distinguish manually entered data and require a separate, informed design.
- Derive a keyed, domain-separated lookup digest from a canonical international phone number rather than store or log the raw number as a lookup key. This is pseudonymization, not anonymization: compromise of the server key enables guessing numbers. Define independent high-entropy secret provisioning, rotation, backup, loss/recovery, deletion and retention before persisting or using real identifiers. Never put keys in mobile builds, source, logs, URLs, analytics or chat.
- SMS OTP proves access to the receiving number at that moment, not a forever-safe account recovery mechanism. Phone recycling, SIM swap, multi-device use and recovery of existing sensitive transactions require explicit security/product design; do not automatically disclose old financial data solely because a future claimant receives a code for the same number.
- On Android, neither a verified login number nor the inbound sender proves which wallet/account a financial SMS belongs to. Dual SIM, device sharing, delayed broadcasts, provider changes and unavailable subscription numbers complicate attribution. The capture boundary must establish a validated active **wallet** session at the SMS arrival/reservation point, constrain scope and consent, and preserve but not assign uncertain messages. Never guess from message content or the currently displayed account.

## What was added, without wiring

`wallet-phone-security.ts` provides strict structural E.164-format input, keyed/domain-separated phone lookup and OTP digests, and separately prefixed random wallet-token hashing. The opaque wallet token is not accepted by existing app-JWT or legacy ingest-token parsing; it is not yet accepted anywhere. The digit check does not establish an allocated or reachable phone number. Secret length validation cannot establish entropy.

`wallet-phone-otp-store.ts` is an unwired Redis challenge building block. It generates a six-digit code and random challenge ID, stores only the ID and keyed digest, and uses Lua to atomically enforce five-minute challenge lifetime, 60-second cooldown, five issuance attempts per phone per hour, five guesses per challenge, and 20 verification attempts per phone per hour. Atomic snapshot comparison prevents an old verification from consuming a replacement; only one concurrent correct verification succeeds. All keys for one lookup share a Redis Cluster hash tag. The issued challenge and store redact common object serialization/inspection, but explicit access to a code or secret can still leak it and the destination number must be handled by a real delivery adapter. Redis errors do not return a successful verification.

These primitives do **not** constitute a login system. Redis state loss, failover, timeouts, mixed versions and cluster behavior have not been tested; retry limits can be lost on state loss and calls can stall. There are no IP/device/global limits, anti-enumeration response policy, delivery-cost controls, provider consent/privacy review, durable delivery, delivery-order fencing, or transactional binding between code consumption and durable session issuance. A delayed/failed provider call may deliver a code after replacement or lose the only usable code. Those must be resolved before exposing an endpoint, with no pretend successful delivery if an SMS provider is unavailable.

### Unwired provider-delivery orchestration

`WalletPhoneOtpDelivery` accepts an injected SMS adapter; there is **no production provider, route, mobile sign-in or actual delivery**. Its request object redacts normal inspection/JSON, but the adapter necessarily has explicit access to the phone and code. A provider response only means the provider accepted the request, not that a handset received it. A provider rejection becomes a generic error with no provider details; cleanup compares the complete original Redis challenge snapshot before invalidation, and preserves cooldown, issuance and phone-attempt budgets. It will not invalidate a replacement. After provider acceptance, it returns the challenge ID only if the same challenge remains current with more than 30 seconds of TTL. There is no automatic delivery retry.

A provider request already started cannot be recalled; a delayed message can arrive after expiration/replacement or sign-out. The status check is only point-in-time. Failure, timeout or Redis outage during cleanup can leave an uncertain old challenge active: a synthetic Redis test explicitly demonstrates it can still verify if cleanup fails. The caller receives a generic failure, not a promise that the challenge was invalidated. Provider calls or Redis operations can hang; durable delivery ordering, timeouts without pretending cancellation, cluster/failover, anti-enumeration, global/IP/device cost limits and mixed versions remain unresolved. No production endpoint should expose these building blocks until these and atomic OTP-to-durable-session issuance are solved. A challenge key that unexpectedly lacks an expiry is now rejected and removed by verification without refunding rate-limit budgets.

The local tests use a fake provider and isolated standalone Redis 6.2, with synthetic numbers only. They do not prove SMS delivery, provider privacy, regional availability, account recovery or mobile/device behavior.

### Unwired PostgreSQL wallet-session groundwork

A separate forward-only migration adds `wallet_accounts` and `wallet_account_sessions` without a phone number, app-user link, financial records, or SMS contents. `WalletSessionStore` can create an **unverified, unbound** wallet principal and opaque one-day session transactionally, hash the credential at rest, revoke it, and serialize a DB-only callback with revocation. It rechecks expiration with the database clock after obtaining the session lock. Runtime grants prohibit updating account/session identity, digest or expiry and prohibit deletion; a trigger makes a committed revocation irreversible. This does not protect against a database owner/superuser or a compromised runtime using its insert privilege to fabricate sessions. The callback must do only work within the supplied DB transaction; it cannot recall network work or prove SMS provenance. A request already holding the lock may finish before revocation, and expiry is checked at the lock boundary, not continuously until commit.

**Do not wire `create()` as login.** It proves no phone control, stores no phone binding, and is not atomically coupled to OTP consumption or delivery. Existing Redis OTP consumption and PostgreSQL session creation are separate operations and can fail independently. Phone number recycling, SIM swap, recovery, account disablement, logout on other devices, retention/erasure of expired sessions and account lifecycle remain undefined. The schema intentionally lacks runtime delete permissions; operational cleanup and user deletion need an explicitly reviewed, safe lifecycle design before real data. The new token still authenticates no endpoint. These tables do not make legacy messages safe or implement per-record ownership.

Local isolated PostgreSQL tests use the least-privileged runtime role with synthetic data. The new migration was run alone on a fresh test database via `node-pg-migrate` (up then repeat up); that is not a full production migration-chain test. Session tests cover identity and digest constraints, irreversible revocation, permissions, rollback, parallel logout, both orderings of logout versus locked work, and expiration while waiting. [Hosted CI 42135624047](https://github.com/KarimOmarShawky/life-style-app/actions/runs/42135624047) subsequently passed the full fresh/repeated migrations, backend tests and Flutter/Android debug validation on `babea59`. It does not prove phone login, live provider, physical device behavior, or the newer record-store changes.

### Provider recommendation (not selected or activated)

The user asked for a recommendation rather than naming an existing provider. **Twilio Verify is a provisional candidate**, not an approved contract or configured integration: its managed OTP lifecycle and fraud controls are useful for an initial implementation. This is not a claim that it is the cheapest or that it meets the app's legal/privacy requirements. Evaluate Egypt delivery and legal terms with the provider and appropriate counsel, obtain a written price, and secure explicit authorization before opening a paid account or sending messages.

- On the provider's October 2026 list, managed Verify costs US$0.05 per successful verification plus channel charges; SMS attempts can be charged even if not delivered. If using a custom code rather than provider-managed generation, the verification fee is per created verification attempt. Source: [Twilio Verify pricing](https://www.twilio.com/en-us/verify/pricing).
- For context only, Twilio's separate Programmable Messaging page lists Egypt outbound international/alphanumeric SMS at US$0.3959 per segment as of October 2026, with possible additional carrier fees. This is **not a confirmed Twilio Verify Egypt quote**, and pricing, taxes, routing, sender and retry costs must be confirmed for the actual account: [Egypt SMS pricing](https://www.twilio.com/en-us/sms/pricing/eg).
- Twilio's [Egypt guidelines](https://www.twilio.com/en-us/guidelines/eg/sms) recommend registered sender IDs because local networks may filter messages; domestic and international requirements differ. Confirm sender registration, brand/template, coverage on intended networks, and approved local routing rather than assume delivery or legal compliance. [Verify's consent policy](https://www.twilio.com/docs/verify/consent-opt-in) requires recipient opt-in and retaining evidence of consent.
- The [Verify RCS terms](https://www.twilio.com/en-us/legal/service-country-specific-terms/verify-rcs) say Twilio may choose RCS or SMS and describe Google as an RCS subprocessor. The user selected SMS: verify SMS-only behavior/terms before any commitment; do not silently activate RCS or another channel.
- The current experimental delivery interface assumes the application generates its own OTP. Provider-managed Verify instead owns generation and checking, so its safe integration needs a separate design for provider approval, attempts, durable one-use session creation, replay/outages and verification receipt handling. Do not wire it as if it were the existing custom-code adapter or conflate provider acceptance with successful delivery. Twilio's [custom-code documentation](https://www.twilio.com/docs/verify/api/customization-options) also requires enabling the feature and providing feedback. Any integration must transmit **only the login OTP and destination**, never financial SMS contents, and must be reviewed for logs, retention, subprocessors, abuse and cost caps.

No provider account, secrets, code delivery or real network calls were created by this recommendation. The user must not paste provider credentials in chat. All wallet-account isolation and NO-GO requirements remain.

## Required integration sequence

1. Choose/configure an approved SMS verification provider and commercial/privacy controls without collecting credentials in chat; implement real delivery and verify sender, retention, regional availability and costs. Provider absence/outage must be visible and fail closed, not silently grant access.
2. Design and test a separate wallet-account/session store and dedicated authentication routes with bounded anti-abuse, one-time OTP and durable atomic session creation, expiration, revocation, logout, device recovery and account lifecycle. Keep wallet credentials scoped to wallet/bank data and inaccessible to general app APIs. Address recycled-number and SIM-swap recovery before opening stored financial data.
3. Implement one native capture/session authority shared by every receiver and Flutter engine, plus owner-authenticated, durable record storage and atomic queue transformations/acknowledgments. Ensure the capture decision uses the wallet session active at the defensible capture boundary, not an account read after a delay. Define dual-SIM and ambiguous-number handling. Couple the legacy lock with a working new capture path rather than silently pausing all capture.
4. Build wallet-scoped transaction/review/provider APIs comparing the authenticated wallet principal against immutable record ownership. Legacy app routes and `X-Wallet-Owner` do not provide this guarantee and must not be used as an unsafe fallback. Preserve unknown-owner old records, without automatically displaying, sending, reassigning or deleting them.
5. Test logout/transition/in-flight races, storage failures, real provider constraints, rate-limit durability, mixed versions, physical Android capture and Focus Shield. A safe quarantined-message interface comes only after isolation; no automatic resend or deletion.
