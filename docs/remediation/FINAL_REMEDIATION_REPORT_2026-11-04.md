### P0-2 — money invariants: backend changes with hosted and UX verification pending

**Root cause:** Validation rounded stored values or checked a different amount from the one inserted; subscription and budget partial updates did not validate effective currency and categories, and the transaction repository could bypass lock-time validation without a user date.

**Fix:** `money.invariants.ts:63-101` validates the exact input or reconstructs recorded scale without discarding nonzero digits, and rejects unknown historical scale unless an amount is supplied. Service and PostgreSQL repository validate effective transactions, subscriptions, budgets and payments, including under write locks; category reads for updates/payments are locked against archive. Payment validates and inserts the same amount. Budget creation rejects archived categories.

**Failing-first proof:** Against a disposable PostgreSQL 16.15 database with forward migrations, `npm --prefix backend test -- tests/integration/money-effective-record-regression.test.ts` initially reported `5 failed | 3 passed`: locked transaction currency, invalid JPY payment, invalid JPY subscription amount, archived subscription category and invalid JPY budget update were all accepted. A same-or-wider currency regression test also first failed (`1 failed | 11 passed`) and then passed. After fixes the file reports `15 passed`, including the required untouched rows and exact payment amount. Existing `money-flow.test.ts` and `money-invariants.test.ts` passed in the same run (`35 passed` total).

**Additional failing-first HTTP and concurrency proof:** On PostgreSQL 16.15/Redis 7.2.11 with the `lifestyle_app` role, the four `P0 effective money records over HTTP` cases were run with pre-`5a39f65` money files restored temporarily: `4 failed` (HTTP 200 instead of 400 for invalid subscription and archived category, HTTP 201 instead of 400 for an invalid JPY payment, and HTTP 201 instead of 409 in a concurrent payment). Files were restored immediately after that run. Against the immediately preceding implementation, `npm --prefix backend test -- tests/integration/money-effective-record-regression.test.ts` reported `2 failed | 15 passed`: the stale payment resolved instead of rejecting and two concurrent payments both succeeded. A separate focused repository test showed two failures because a future date and an absent validation date were accepted. The focused HTTP race reproduced `expected 201 to be 409`. PostgreSQL row locks and `pg_blocking_pids` coordinate the race rather than mocking the repository. After the fix, `npm --prefix backend test -- tests/integration/money-flow.test.ts tests/integration/money-effective-record-regression.test.ts tests/unit/money-invariants.test.ts` reported `3 passed` files / `43 passed` tests. The real-DB race file also passed five repeated runs.

**Payment race fix:** `money.service.ts:595-652` supplies the observed subscription version, unmodified request, and a single user-local date. `money.repository.pg.ts:907-1006` acquires `FOR UPDATE`, rejects a changed or missing version with 409, validates the exact locked/overridden amount and occurrence date, and computes the next cycle from the locked row before inserting the same validated value. Tests cover simultaneous payments, a concurrent update, missing validation date/version, future payment date, unchanged rows, archived categories and exact KWD payment through HTTP. This relies on all application subscription writers incrementing `version`; out-of-band SQL writes that bypass versioning are not fenced by a database trigger.

**Selected scale policy and failing-first evidence:** The user selected saving the original input scale for new amounts and requiring an explicit amount on every edit of historical rows whose input scale is unknown. The new forward-only `1792500000000_money_input_scale.cjs` adds nullable `amount_scale` to transactions, subscriptions and budgets, with bounds and numeric-consistency checks; historical values are not guessed or backfilled. `schema.sql` and `schema-sql.ts` were updated without altering applied migrations. A payment on a legacy subscription requires an explicit payment amount; it does not claim this override was the subscription's original scale. Deletion remains possible without re-entering a value. Before the fix, `npm --prefix backend test -- tests/integration/money-scale-regression.test.ts` reported `3 failed`: USD `10` to JPY returned 400 instead of 200, legacy edits returned 200 instead of 400, and legacy payment returned 201 instead of 400. The new schema snapshot guard failed `1 failed | 6 passed` before adding the columns. After the fix, the complete money and snapshot targeted run reported `5 passed` files / `54 passed` tests, including the three behavioral cases and database constraint checks. Existing test fixtures were augmented with known input scales, without changing their behavioral assertions; one test's direct SQL injection explicitly resets its scale to NULL to model a historical invalid value.

**Upgrade and residual:** In a separate isolated PostgreSQL database, the ten prior migrations were applied, three old money rows were inserted, the new migration was applied and repeated, and the IDs, values, currencies and versions were verified unchanged with NULL provenance (`PASS: three pre-existing rows unchanged and provenance unknown after upgrade`; second `migrate:up`: `No migrations to run!`). Migration rollout must precede code rollout, and direct SQL writers must keep amounts, scale and versions consistent. P0 is not signed off.

### P1-1 — DATE boundary: partial

**Root cause:** `pg`'s default DATE parser returns `Date`, despite the Kysely DATE declarations being strings; goal partial-update comparison could compare a `Date` to a string, and relative reminders expect a string.

**Fix:** `backend/src/infrastructure/database/postgres/pool.ts:16` registers the OID 1082 string parser (option A). `backend/src/features/goals/goals.service.ts:105` normalizes both effective dates before comparison, including legacy `Date` values.

**Failing-first proof:** `npm --prefix backend test -- tests/unit/date-pg-boundary-regression.test.ts` before the fix: `2 failed`; parser assertion received `2026-02-03T00:00:00.000Z` instead of `'2026-02-03'`; the goal test received HTTP status 409 instead of 400. After: `2 passed`. The goal test uses a stub repository, not a database.

**Regression risk / residual:** Globally changing the parser affects every PostgreSQL DATE consumer; the full existing PostgreSQL integration suite passed, but the requested new relative-reminder and partial-goal HTTP acceptance tests were not added or run. Do not consider the P1 acceptance criteria satisfied until those are exercised, including existing DATE consumers.

### P1-3 — list cursors: partial

**Root cause:** Three repositories silently ignored decode errors and permitted non-UUID IDs to reach PostgreSQL; SQLSTATE `22P02` fell through to 500.

**Fix:** `backend/src/core/http/created-at-cursor.ts:4` validates the emitted base64 JSON format, UUID and ISO timestamp; habits, projects and recurring-task list repositories call it before execution (`habits.repository.pg.ts:245`, `projects.repository.pg.ts:184`, `recurring-tasks.repository.pg.ts:317`). `backend/src/core/middleware/error-handler.ts:174` maps `22P02` to a safe 400.

**Failing-first proof:** `npm --prefix backend test -- tests/unit/list-cursor-regression.test.ts` before: `4 failed`, with all three invalid cursor cases resolving instead of rejecting and the SQLSTATE handler returning 500 instead of 400. After: `4 passed`. Tests use stub query builders and a real Express error-handler request; they do not exercise authenticated endpoints with PostgreSQL.

**Regression risk / residual:** Invalid or old cursors that were previously ignored now produce 400, intentionally. The decoder accepts the canonical timestamps emitted by these repositories; verify successful pagination and malformed-cursor HTTP responses against a real database before release.
